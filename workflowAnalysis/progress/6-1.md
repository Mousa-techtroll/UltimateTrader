# Phase 6.1 — Trade-error/retry classifier on retcode, not GetLastError (Infra-1)

> Iteration 6. The trade-error/retry classifier (`CEnhancedTradeExecutor::HandleExecutionError` →
> `CErrorHandlingUtils::HandleTradingError`) switched on **MQL4-era error codes** (6/136/138/129/135/132/134…)
> fed by `GetLastError()`, NOT the MQL5 `m_trade.ResultRetcode()`. So retry/no-retry decisions were made on
> the WRONG code space → wrong retries (or wrong halts) on real broker errors. Fix = RETCODE-FIRST classifier:
> capture `ResultRetcode()` after the trade call; classify on `TRADE_RETCODE_*` as PRIMARY; fall back to the
> KEPT legacy `GetLastError()` switch ONLY when `retcode==0`. **Live-only** classification correctness — but
> the tester DID surface ONE retryable-looking retcode (`TRADE_RETCODE_MARKET_CLOSED` 10018 on weekend-gap
> signals), so the A/B is **byte-identical on all EXECUTED trades** (Stats/TradeEvents/Candidates + headline)
> with a 13-row delta confined to `EXECUTION_FAILED` diagnostic rows in the Risk CSV — see byte-identity proof.

### Retry CAP enforcement (fix point 6) — confirmed
The cap is enforced on TWO independent axes (both pre-existing + preserved): (1) the retry loop bound `for(int attempt=0; attempt < m_maxRetries; attempt++)` (CEnhancedTradeExecutor.mqh:1359) hard-limits total attempts to `m_maxRetries` (default 3); (2) every RETRY case sets `shouldRetry = (attemptNumber < maxAttempts - 1)`, so the classifier itself refuses to retry on the last allowed attempt. A chased REQUOTE therefore cannot fill many-points-worse beyond 3 attempts; `UpdateParametersForRetry` re-anchors price/SL/TP to refreshed market data each attempt.
