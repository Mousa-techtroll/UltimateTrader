# Phase 5.10 — File-signal deferred-commit (XCut-1)

> Iteration 5. A file/Telegram signal was marked permanently `Executed` (durable, never-retry)
> at EMIT time — BEFORE the orchestrator could reject it (slippage / risk / exposure gate). A
> transiently-rejected signal was therefore LOST forever even though it was never actually traded.
> Fix = DEFERRED-COMMIT: keep an OPTIMISTIC array flag at emit (stops same-tick re-emit) but defer
> the durable `MarkExecuted` to a CONFIRMED fill (`ticket>0`); on a reject, roll the optimistic flag
> back so a later in-window tick can retry. **Live-only** — file signals never fire in the tester
> (no `telegram_signals.csv` in the data dir), so the deferred-commit path is never entered → the
> A/B is byte-identical (no production regression); correctness rests on the code logic.

### `Include/EntryPlugins/CFileEntry.mqh`
- **New members (80-81):** `int m_pendingTradeIdx;` (index into `m_trades` of the in-flight signal, `-1`=none) + `string m_pendingTradeKey;` (its persistent dedup key). Seeded in the ctor (631-632) `m_pendingTradeIdx=-1; m_pendingTradeKey="";`.

Diagnostic changed `SIGNAL READY` → `SIGNAL EMITTED (pending) … awaiting fill confirmation`.
- **New `ConfirmExecuted()` (681-694, public):** no-op if `m_pendingTradeIdx < 0`; else `if(m_pendingTradeKey!="" && !IsAlreadyExecuted(...)) MarkExecuted(m_pendingTradeKey);` → durable commit; clears the pending slot. Idempotent. Prints `FILL CONFIRMED … committed (never-retry)`.
- **New `RollbackPending()` (706-725, public) — BOUNDS-GUARDED:** `if(m_pendingTradeIdx >= 0 && m_pendingTradeIdx < ArraySize(m_trades)) m_trades[m_pendingTradeIdx].Executed = false;` (re-enable retry; durable key never committed so the signal can fire again on a later in-window tick). Stale-index branch (idx>=0 but out of range after a reload shrank `m_trades`) logs + does nothing to the array (key was never committed → still retryable). Always clears the pending slot at the end. Prints `REJECT — rolled back … retry enabled (not consumed)`.

### `UltimateTrader.mq5` (file-signal execution result site)
- **On success (`filePos.ticket > 0`, ~2255):** added `g_fileEntry.ConfirmExecuted();` after `AddPosition`/`IncrementTradesToday`/`RecordExecutionSuccess` → durable commit only on a confirmed fill.
- **New `else` branch (reject, `ticket<=0`, ~2266):** added `g_fileEntry.RollbackPending();` → clears the optimistic flag so the signal can retry on a later in-window tick.

- **Diff summary:** durable `MarkExecuted` moved out of the emit path into a fill-confirmed `ConfirmExecuted()`; a reject now calls the bounds-guarded `RollbackPending()` instead of silently consuming the signal. Optimistic array flag retained at emit to prevent a same-tick re-emit loop.

The dedup key-set, `IsTradeReadyForExecution` window, and reload logic are unchanged. The only behavior change: a REJECTED file signal is now retryable instead of lost.

## WHY (live-only; the deferred-commit logic)
- **The fix's VALUE is not measurable in the tester.** File signals are read from `telegram_signals.csv` in the data dir's `Files\`. That file is ABSENT in the tester → `LoadTradesFromFile()` loads 0 trades → `CheckForEntrySignal()` never emits → `m_pendingTradeIdx` stays `-1` → `ConfirmExecuted()`/`RollbackPending()` are never reached. So the deferred-commit path is dormant in the backtest; the byte-identical A/B proves only that no PRODUCTION regression was introduced.
- **Correctness rests on the code logic (reviewed, not measured):**
  1. **Optimistic flag stops the re-emit loop** — at emit, `m_trades[i].Executed=true` makes `IsTradeReadyForExecution` return false for that entry on the SAME tick's loop and on subsequent ticks UNTIL a result is processed, so the orchestrator isn't hammered with the same signal repeatedly.
  2. **`ConfirmExecuted` only on `ticket>0`** — the durable `MarkExecuted` (which survives file reloads via `m_executedKeys`) fires solely on a confirmed fill, so a truly-traded signal is never re-traded.
  3. **`RollbackPending` re-enables retry on reject** — on `ticket<=0` (slippage / risk / exposure gate), the optimistic flag is cleared (durable key NOT committed), so the NEXT in-window tick re-evaluates the signal. The pending index is **bounds-guarded** (`>=0 && < ArraySize(m_trades)`) so a file reload that shrank `m_trades` between emit and result cannot cause an OOB write; the stale-index case logs and leaves the (uncommitted) key retryable.
  4. **The slippage gate self-rejects stale retries** — `ExecuteSignal`'s existing `InpFileMaxSlippagePct` check drops a retry whose live price has drifted too far from the original entry, so a recovered-but-stale signal is correctly NOT chased. No extra retry-window logic was added (per directive).
- Because emit→execute→confirm/rollback all happen synchronously within one `OnTick` iteration, the pending slot is always resolved before the next `CheckForEntrySignal`, so `m_pendingTradeIdx`/`Key` always describe the just-emitted signal.
