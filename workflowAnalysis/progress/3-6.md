## Byte-identity investigation (QA(a) note — required because GetDayType IS reachable on production)
- The task's QA(a) anticipated: *"router off → GetDayType shouldn't affect production unless GetDayType is read on the production path — check + report."* It IS read on the production path: **CExpansionEngine (a LIVE legacy engine on the production `.set`) stamps `signal.day_type = m_context.GetDayType()` unconditionally** (`CExpansionEngine.mqh:581`, inside `TagAndScore`, runs regardless of `m_scorer`). `signal.day_type` → `position.day_type` (`CTradeOrchestrator.mqh:632`) → `pos.day_type` → the **DayType column in the TradeEvents/Candidates CSVs** (`CTradeLogger.mqh:250/581/766/437`). So if `GetDayType()` returned DAY_DATA on a bar where a production Expansion trade fires, the telemetry CSV would DIVERGE (a "DATA" string instead of "TREND"/"VOLATILE"). The decision-path `m_day_type` (CExpansionEngine:453/480, CLiquidityEngine:365/416) is sourced from `CDayTypeRouter.ClassifyDay()` (via `SetDayType`, mq5:1525-1528), which does NOT call CMarketContext.GetDayType and never returns DAY_DATA — so trade DECISIONS are unaffected, but the CSV telemetry would not be.
- **Resolution (the byte-identity gate):** `IsDataDay()` is gated behind `InpEnableMultiStrategy`. On the production `.set` (`InpEnableMultiStrategy=false`) it is constant-false → `GetDayType()` never returns DAY_DATA → the CExpansionEngine telemetry stamp keeps its pre-3.6 value → CSVs byte-identical. This matches the plan's stated invariant ("the router/GetDayType DAY_DATA path is consumed only when InpEnableMultiStrategy=true"). News-flat is fully exercised at the engines-ON GATE (router ON, where DAY_DATA both gates engine weight AND stamps telemetry).
