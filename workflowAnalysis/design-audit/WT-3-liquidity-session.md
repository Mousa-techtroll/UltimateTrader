## §10 — LIQUIDITY MAP TEST — SCORE: 3 / 5 (Acceptable beta)

### What exists (the genuinely professional parts)

**A real, multi-source obstacle/liquidity map feeds a TARGET-REACHABILITY gate.**
`CTradeOrchestrator::FindNearestObstacle()` (CTradeOrchestrator.mqh:1016–1090+) aggregates, per direction, the nearest of: confirmed H4 swing pivots (2-left/2-right, read from CLOSED bar shift 1 — no repaint), **prior-day high/low** (:1045), **prior-week high/low** (:1050), **$50 round-number** psychological levels (:1055), and **active SMC supply/demand OB zones** via `GetNearestSMCResistance/Support` (:1062). The reward-room check at :360–390 then rejects the trade when room-to-first-obstacle `< InpMinRoomToObstacle` R. This is exactly the professional discipline the rubric §10 demands ("avoid entering directly into obvious opposing liquidity unless that is the target"; "Trade is not directly into ___"). It is a real geometry gate, explicitly separated from quality, and it is wired into the live path. **This is the single strongest liquidity feature in the system and is why this is a 3, not a 2.**

**A serious zone framework is built.** `CSMCOrderBlocks.mqh` models bullish/bearish OBs (last-opposite-candle + ATR-impulse + body-% filter, :788–835), FVGs (3-candle gap with min-gap floor, :854–876), equal-high/low liquidity pools with **ATR-derived tolerance** (:1023–1032, capped 80pt to prevent structural misclassification) and a touch-count minimum, BOS/CHoCH on closed bars (:956–1004, correctly anchored to shift 1), and sweep detection with a **recency window** (`SMC_SWEEP_RECENCY_BARS=3`, :18, :1135–1152) that fixes a permanent stale-latch. The engine knows buy-side liquidity rests below (equal lows) and sell-side above (equal highs) (:1605, :1633) — correct ICT semantics.

**The displacement entry is sweep-aware and grades the swept level.** `CheckDisplacement` (CLiquidityEngine.mqh:530–769) requires a wick beyond swing + close back inside (true sweep, not a clean breakout) and then scores the swept level's importance via `ScoreLiquidityLevel` (:1489–1512): prior-day H/L → 3, weekly H/L → 4, strong SMC zone → 3, else minor swing → 1, with a `liq_score >= 2` gate (:587). So the EA **does distinguish a sweep from a clean breakout** and **does prefer sweeps of structurally important pools** — both rubric pass-criteria.

### Design gaps (why it is capped at 3)

1. **Liquidity-as-explicit-TARGET is dead code (file:CSMCOrderBlocks.mqh:625–643, :596–1647).** `GetOrderBlockTargetLevel()`, `GetOrderBlockStopLevel()`, `FindNearestLiquidityAbove/Below()` and the whole `SLiquidityPool nearest_buy/sell_liquidity` apparatus are **never consumed anywhere** (verified: grep finds zero callers outside the class; the only external SMC-zone consumers are `GetNearestSMCResistance/Support`, used for the obstacle filter, NOT for setting TP). Every engine target is instead a **fixed R-multiple**: displacement TP = risk × 2.5 (CLiquidityEngine.mqh:631), OB-retest = risk × 3.0 (:837), FVG = ×2.5 (:1022), SFP = ×2.5 (:1290); session modes = ×2.0 (CSessionEngine.mqh:693) or a 50%-extension retrace (:1193). **Pro comparison:** a professional targets the *opposing liquidity pool* (next equal-high cluster, PDH, naked POC) and sizes R to it; here the map is used to *veto* a trade with no room, but never to *place* the take-profit. The rubric explicitly asks "Does it use liquidity as target logic?" — the answer is the obstacle veto only, not TP construction. **Fix:** route `takeProfit1` to `FindNearestObstacle` / nearest unswept opposing liquidity pool (clamped to a min-R floor), instead of a blanket 2.5R. **Confidence: HIGH** (grep-verified dead code + every TP is a literal R-multiple).

2. **The OB stop-placement helper is also unused; stops are ATR/structure-of-the-pattern, not pool-aware buffered.** `GetOrderBlockStopLevel` (:602) would place stops beyond the OB with a 0.5-ATR buffer, but it is dead. Live stops are sweep-extreme ± ATR buffer (displacement, :625), ATR×0.8 (OB-retest, :831), ATR×1.0 (FVG, :1016), or wick-extreme + buffer (SFP, :1284). These are *reasonable* and do carry a buffer beyond the swept wick — so the §10 red-flag "stops placed exactly at obvious equal-highs/lows without buffer" is **avoided**. But the stop is placed relative to the *triggering pattern's* extreme, not validated against the *nearest equal-high/low pool* the map knows about, so a stop can still sit just inside an un-mapped cluster. **Confidence: MEDIUM.**

3. **Liquidity pools and OBs are H1-only (CSMCOrderBlocks.mqh:246, :779–782, :889, :1019).** Every scan (`CopyHigh/Low(PERIOD_H1...)`) and the ATR handle are H1. There is **no current-day H/L tracking as a liquidity object** (current-day extremes appear only as the daily-range denominator in `GetLocationPenalty`, CLiquidityEngine.mqh:1519), **no daily-open or weekly-open level**, and no HTF (H4/D1) OB/FVG layer. The rubric's level list wants previous-day H/L (present, via obstacle filter), current-day H/L (absent as a pool), daily/weekly open (absent). A pro maps the daily open and the prior session H/L as primary draws; this map is missing them. **Confidence: HIGH** (all Copy* calls are PERIOD_H1/D1-prev/W1-only; no SYMBOL daily-open read anywhere in scope).

4. **`GetNearestSMCResistance/Support` only scans OB zones, ignoring the equal-high/low liquidity pools the same class maintains** (CMarketContext.mqh:573–587 → `GetNearestZoneAbove/Below`, which iterate `m_bullish_obs/m_bearish_obs` only). So the obstacle filter's "SMC" leg sees order blocks but is blind to the very equal-H/L pools that are the textbook liquidity targets. **Fix:** include unswept `m_liquidity_pools` in the nearest-obstacle scan. **Confidence: HIGH.**

5. **Equal-H/L detection is O(n²) nearest-by-array-index, keeping the FIRST qualifying level, not the strongest/closest, and pools never refreshed beyond 50-bar H1 lookback** (CSMCOrderBlocks.mqh:1037–1096, `ob_lookback=50`). Functional, but the pool set is shallow and index-order-dependent. **Confidence: MEDIUM.**

### §10 verdict
A legitimate liquidity framework exists and — critically — it *gates* entries by reachable room to real structure (PDH/PDL, PWH/PWL, round numbers, H4 pivots, OB zones). That earns a solid Acceptable. It is capped at **3** because the map is used almost entirely **defensively (veto)** and never **offensively (target placement)**, the richest liquidity objects (equal-H/L pools, daily/weekly open, current-day H/L) are either dead code or absent, and the whole structure is H1-only with no HTF liquidity layer.

## §11 — SESSION INTELLIGENCE TEST — SCORE: 2 / 5 (Present but weak / easy to break)

### What exists

**A real GMT session clock with configurable broker offset.** `CSessionEngine` (CSessionEngine.mqh) defines Asian (0–7), London (8–10), NY (13–14), Silver-Bullet (15–16), London-Close (16–17) GMT windows (:33–42), converts server→GMT via `GetGMTHour` (:460–468), and **auto-detects the offset** from `TimeCurrent()-TimeGMT()` with a configurable backtester fallback `InpBrokerGMTOffset` (:311–330). Modes are **mutually exclusive by GMT hour** and dispatched in a time-gated cascade (:388–454) — the EA genuinely *knows which session each setup is for*, a rubric pass-criterion. `GetGMTHour` is exposed as a public service and reused (e.g. SFP session tagging, CLiquidityEngine.mqh:1176). **This is the strongest §11 feature.**

**Asian range is treated structurally and differently from expansion.** Phase 1 (:388–393) only *builds* the Asian high/low (no signal) on M15 granularity (:559–600), **validates** the range against ATR bounds (min 0.5×, max 2.0× ATR, :611) so only genuine compression ranges qualify, then **freezes** it (:617). London/NY then trade the *breakout/continuation* of that frozen range (:651, :787). So Asian-vs-expansion differentiation and session-H/L definition both exist — two rubric pass-criteria. This maps to the professional Scenario-3/Scenario-4 expectation.

### Design gaps (why it is capped at 2)

1. **CRITICAL — No rollover / dead-liquidity / late-session BLOCK anywhere (rubric §11 red flag: "It opens new positions during rollover or dead liquidity").** Searched the entire Include tree and EA: there is **no time-of-day trade block** for the ~21:00–23:00 GMT rollover spread-widening window, no NY-close block, and no "stand-aside in Asian dead range." `CPinBarEntry` self-excludes Asia (gmt 8–23, CPinBarEntry.mqh:233) but that is one plugin's internal filter, not a system-wide session gate. The only illiquidity protection is **reactive**: the executor's shock detector (CEnhancedTradeExecutor.mqh:2150) hard-blocks only on a **spread spike >3× recent average** — i.e. it catches rollover *after* the spread has already blown out, not by clock. A professional blocks the clock window proactively because the first rollover tick can gap a stop before the spread sample even updates. The rubric asks directly "Does it block new trades near rollover?" — **no.** **Fix:** add an `InpBlockRolloverStart/End` GMT gate in the orchestrator that rejects new entries in the broker's rollover window, plus an optional Asian-session new-trade throttle. **Confidence: HIGH** (exhaustive grep; no rollover/22:00/23:00/NY-close block exists outside comments).

2. **The session engine's own analysis (§ at line 105–106 in scope) says its session setups are largely disabled, yet the session *clock* is load-bearing — a structural tension.** `m_enable_silver_bullet=false` and `m_enable_london_close=false` by default (CSessionEngine.mqh:105–106); London-BO and NY-Cont default on (:103–104) but per-mode auto-kill (PF<0.9@15, <1.1@30, neg-exp@40, :476–513) can disable them. So the session *intelligence that shapes entries* (which session → which setup) can self-erase to nothing while the clock still runs only to time-gate. **Per memory/Honest-baseline this engine "can't be deleted yet" because it is the live GMT clock** — i.e. the architecture keeps a 5-mode session-entry engine alive mostly for its `GetGMTHour` service. From a design-purity standpoint the session-INTELLIGENCE layer (vary behavior by session) is thinner than the file size suggests. **Confidence: MEDIUM-HIGH** (defaults + kill thresholds are explicit in source).

3. **No per-session trade-frequency limits (rubric: "different trade frequency limits by session").** Modes are time-gated to fire at most once per bar in their window, but there is no notion of "max N London-breakout attempts/day" or reduced Asian frequency beyond the binary on/off window. The Asian range itself is build-only (good), but London/NY have no session-scoped count cap visible in scope. **Confidence: MEDIUM** (no per-session counter in CSessionEngine; daily caps live elsewhere — `InpMaxPositions`/daily-loss — but those are not session-aware).

4. **NY window is extremely narrow and US-DST-blind.** `m_ny_start=13, m_ny_end=14` (:95–96) = a single GMT hour, and Silver-Bullet 15–16 GMT. ICT's NY AM killzone/Silver-Bullet is anchored to **New York local time (10:00 ET)**, which is 14:00 GMT in winter but **13:00 GMT in summer (EDT)**. The fixed GMT hours drift one hour against the actual NY session twice a year. A pro anchors killzones to exchange-local time. **Confidence: HIGH** (hours are integer GMT constants; no DST handling on the US side anywhere in scope; only broker-offset DST is auto-detected, not the NY-session DST).

5. **Weekend close exists but no Friday-late new-trade block (Scenario 19).** `CPositionCoordinator` closes positions Fri at `m_weekend_close_hour` (CPositionCoordinator.mqh:1713–1718) — good for *exiting* — but I found no gate preventing *opening* a fresh late-Friday position before that hour. **Confidence: MEDIUM** (close logic confirmed; no symmetric open-block found in scope).

### §11 verdict
The GMT clock, offset auto-detection, Asian-range structural treatment, and session-H/L definition are real and competent — that floor keeps it off a 1. But the **absence of any proactive rollover/dead-liquidity time block** is a named §11 critical red flag, the killzone hours are DST-blind, there are no per-session frequency limits, and the session-entry intelligence largely defaults off (clock-as-service). Weakest-critical-area rule applies: the missing rollover block caps this at **2**.

## Cross-cutting note (affects both sections)
The liquidity map (PDH/PDL/PWH/PWL/round/H4-pivot/OB) lives in the **orchestrator's obstacle filter**, while the session H/L and Asian range live in the **session engine**, and the SMC pools live in **CSMCOrderBlocks** — three separate maps that don't share a single liquidity registry. The session H/L are never fed into `FindNearestObstacle`, and the equal-H/L pools are never fed into either the obstacle scan or TP placement. Unifying these into one liquidity object that serves bias, obstacle-veto, AND target would materially raise both scores.

## SCORES
- **§10 Liquidity Map: 3 / 5** — real multi-source obstacle/reachability gate (PDH/PDL/PWH/round/H4/OB) + sweep-vs-breakout discrimination + buffered stops; capped by liquidity-as-target being dead code, equal-H/L pools unused by the obstacle scan, and H1-only with no daily/weekly-open or current-day-H/L pool.
- **§11 Session Intelligence: 2 / 5** — competent GMT clock + offset auto-detect + structurally-frozen ATR-validated Asian range + session H/L; capped by NO proactive rollover/dead-liquidity time block (named red flag), DST-blind killzone hours, no per-session frequency limits, and session-entry modes largely defaulting off.
